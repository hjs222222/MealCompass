## 0. 一分钟看懂：这个项目"能讲什么"

**一句话**：一个多约束菜谱推荐 Agent——**硬约束下推到检索层**保证推荐安全，**混合检索 + RRF + 重排**保证召回质量，**LLM 只负责解释与取舍**，所有推荐都要通过**引用校验**指向知识库里真实存在的菜谱。

**三条主线**（面试时按需展开，不要一次全说完）：

| 主线 | 核心动作 | 可指的代码 | 可说的数字 |
| --- | --- | --- | --- |
| **检索** | 向量 Top50 + BM25 Top50 → RRF → 重排 Top10 | `backend/rag/retriever.py` | 三组消融的 Recall/nDCG（`data/eval/reports/`） |
| **Agent** | `parse → search →（无解短路）→ generate → validate` | `backend/agents/graph.py` | `node_path` 可解释性；降级路径有测试 |
| **可信** | 硬约束 SQL 下推 + 领域层引用校验 + 诚实登记未做项 | `backend/domain/citations.py`、`docs/failed-features.md` | 单测数、覆盖率、CI 门禁 |

**不要主动说**（会被追问，而你答不上或没必要）：7 节点编排、多智能体、RAGAS 四项指标、多轮对话、鉴权、购物清单。这些**明确没做**，被问到就照 `docs/failed-features.md` 说"主动推迟 + 理由"。

## 2. 自我介绍：三个时长版本

### 30 秒（电梯）

> "我做过一个菜谱推荐 Agent。和普通'今天吃什么'不同，它把忌口、厨具、时间做成**硬约束下推到数据库检索层**——LLM 不参与判定，所以不会推荐你过敏的东西。检索我用了**向量 + BM25 + RRF + 重排**，然后自建了 40 条评估集做消融实验。**结果很有意思：混合检索反而比纯向量差**——我定位到根因是 RRF 等权融合的一个结构性不等式，让 BM25 任何一次命中都能把一道菜升格成'共识项'并获得优先权，等于系统性惩罚了向量通道。**这个负面结论比一个好看的指标更能说明问题。** LLM 只负责把查询翻译成约束、把候选菜谱解释成人话，而且任何推荐都要通过**引用校验**，编造的菜谱会被丢掉。"

### 2 分钟（技术面开场）

在 30 秒基础上，加三段"为什么"：

1. **为什么先做消融而不是直接上混合**：混合检索听起来更高级，但"两路各取 Top50 用 RRF 融合"是一个**未经检验的假设**。我建了 40 条人工评估集把它套出来——**结果假设被否定了**。我发现等权 RRF 有一个恒成立的不等式：单通道项上界 `1/(k+1)=0.016393` < 双通道项下界 `2/(k+50)=0.018182`，所以**只要一道菜两路都进 Top50，它必然排在所有单通道候选之前**，哪怕两路都排第 50。7 条回归查询的 21 个金标准里「仅向量」的有 13 个，向量明明把它们排在第 1，却被整片"共识集合"压到 20 名开外（`西红柿炒鸡蛋` 向量 #1 → RRF 第 22）。
2. **为什么硬约束下推**：如果在检索后才过滤，Top10 里可能 8 条都是违规的，候选质量完全没法保证。下推到 SQL 之后，召回池本身就是"合法集合"。而且 BM25 是内存语料检索，**不能**继承向量通道的 Top50 边界，否则它就失去独立召回价值——这点我专门写了测试。
3. **为什么引用校验放在领域层**：幻觉不是提示词能解决的，是**校验**能解决的。`domain/citations.py` 是纯逻辑零 IO，所以可以直接单测；LLM 返回的每个 `recipe_id` 必须在候选集合里精确命中、菜名还要一致（防止"用对的 ID 配错的菜名"），否则丢弃。

### 5 分钟（深挖面）

再加上：数据管线（"不编造"原则怎么落地、解析层噪声清理把待确认用量从 86 条降到 25 条）、降级契约（LLM 挂了会怎样，`recommendation_shortfall` 的精确触发条件）、以及**没做什么**（诚实边界，见第 8 节与 `docs/failed-features.md`）。

## 3. 检索 / RAG 深挖（最可能被追问的部分）

### Q3.1 为什么用 RRF 而不是加权求和分数？

**答**：向量的余弦距离（0~2）和 BM25 的分数（无上界、随语料变化）量纲完全不同，加权求和需要归一化，而归一化方式不同结果就不同，调参不可复现。RRF 只用**排名**：`score(d) = Σ 1/(k + rank_i(d))`，k=60 是论文默认值。排名是天然可比的，而且对单路分数漂移鲁棒。

**能指**：`backend/rag/fusion.py`（含 docstring 引了 Cormack et al. 2009）。

**追问：k=60 怎么来的？** 论文默认值。k 越大，头部优势越小、多路共识越重要；k 越小越偏向单路的第 1 名。我们没有调这个参数（可以诚实说"没有做 k 的敏感性实验，这是可以改进的方向"）。

**追问：同分怎么办？** `fusion.py` 里按 `(通道下标, 排名)` 做了稳定排序，保证结果确定、不抖动。

### Q3.2 硬约束怎么"下推"的？具体到 SQL。

**答**：`HybridRetriever._allowed_recipe_statement()` 先构造一个只含合法 `recipe_id` 的子查询：

- **厨具**：菜谱的 `tools` 必须是用户 `tools_available` 的**子集** → `recipes.tools <@ :tools`（PG 数组包含操作符）
- **时间**：`time_minutes IS NOT NULL AND time_minutes <= :max`——**注意这里刻意排除了 NULL**，因为当前解析未提取部分原文明示的全程时长，未知时长按严格安全语义不能算"满足约束"
- **忌口**：`NOT EXISTS` 三层匹配——标准名 `ingredients.name`、原文 `recipe_ingredients.name_raw`、别名 `ingredient_aliases.alias`，全部 `.lower()` 后比较

然后这个集合**分别**约束向量通道和 BM25 通道。

**能指**：`backend/rag/retriever.py` + `backend/tests/unit/test_retriever_filters.py`（把 SQL 编译成字符串断言谓词存在）。

**高分细节（一定要说）**：BM25 是**内存语料**检索，**不能**继承向量通道的 Top50 边界。代码里专门注释了这点，测试也单独覆盖了——如果 BM25 的候选池只有向量 Top50，那它就完全失去独立召回价值了。

**追问：为什么用 `.lower()` 而不是 Python 的 `.casefold()`？** 因为 `.casefold()` 会把 `ẞ` 折成 `ss`，而 PostgreSQL 的 `lower()` 不会——两边语义不一致会让 SQL 永远匹配不上。这个坑我们踩过（`retriever.py` 里有注释）。

**追问：那这个 `NOT EXISTS` 有没有漏网过？（必问，已经踩过）** 有，而且是个系统性问题，不是单点 bug。实测发现用户说"不要番茄"，结果推荐了"番茄红酱"；说"不要土豆"，结果推荐了"炸薯条"。三层根因：

1. **食材粒度断层（最主要）**：词表里 `番茄`（蔬果）和 `番茄酱`（调料）是**两个独立标准食材**，没有父子层级关系。用户说"不要番茄"，SQL 找的是 `canonical = '番茄'`，而番茄红酱里的食材是"番茄酱"→ canonical=`番茄酱`，精确等值匹配不上。类似的：`土豆淀粉` → canonical=`淀粉`（不是土豆）、`番茄膏` → canonical=`番茄酱`。
2. **解析层噪声泄漏**："炸薯条"这道菜的食材表里只有 `-`、`作为主食，`、`作为小食，` 三条噪声，真正的土豆根本没被解析进 `recipe_ingredients`——硬约束 SQL 压根不知道这道菜含土豆。
3. **SQL 精确等值太死**：`ri.name_raw = '番茄'` 不匹配 `小番茄`（未归一化）、`土豆两三个`（已归一化但 `name_raw` 本身不是"土豆"）。

**这个问题怎么修（讲思路）**：短期是在 SQL 里加 `ri.name_raw LIKE '%番茄%'` 兜底，但要小心误命中；中期是修解析层把炸薯条这种主料丢失的菜重灌；长期是词表加"加工制品 → 父食材"的层级字段，忌口下推时递归展开。**关键认知是：忌口硬约束的可靠性取决于数据归一化的完备度，SQL 写得再对，食材表是空的也没用。**

### Q3.3 双层切分为什么这么设计？步骤层为什么**不加**菜名？

**答**：卡片级（菜名 + 简介 + 食材）用于粗召回"哪道菜"；步骤级（步骤原文）用于精取"怎么做"。

**关键决策**：步骤文档**故意不加菜名前缀**。因为如果每个步骤都带菜名，那么查询"西红柿炒鸡蛋"时，这道菜的**所有**步骤都会强匹配，步骤级排序就被菜名污染了，失去"按技法精取"的意义（比如查"怎么勾芡"）。菜名上下文由检索方按 `recipe_id` 关联回 `recipes` 表补齐。

**能指**：`backend/rag/chunking.py` 的 `build_step_document` docstring。

**追问：为什么卡片文本同时喂向量和 BM25？** 只有喂同一份文本，两路召回的才是"同一个东西"，融合才有意义，结果才可解释。`rag/corpus.py` 和 `scripts/build_index.py` 都走 `build_card_document()` 这唯一构造点。

### Q3.4 重排失败了会怎样？

**答**：**降级回 RRF 顺序**，不是报错。`rag/reranker.py` 用 `try/except` 包住重排，失败时把全部候选标记 `degraded=True`、`rerank_score=None`，返回原顺序。契约是"**重排绝不能拖垮检索**"。

另外：如果重排走了**本地兜底**（`last_provider == "local"`）也算降级路径，同样打标——因为本地模型和远程的排序质量不同，这个事实必须暴露给上层而不是藏起来。

**能指**：`backend/rag/reranker.py`、集成测试 `tests/integration/test_retriever.py` 里有一个 `BrokenRerank` 用例专门验证降级。

### Q3.5 BM25 语料放内存，规模上去了怎么办？

**诚实答**：当前 372 张卡片，内存 BM25 建一次只要一次 SQL + jieba 分词，完全够用，而且省掉一个服务。**规模上去（比如 10 万条）就需要换方案**：

- 方案一：用 PostgreSQL 的 `tsvector`（我们已经建了 `recipe_embeddings.tsv`，用 jieba 分词后 `to_tsvector('simple', ...)`）——但 `ts_rank` 不是 BM25，效果会退化；
- 方案二：上 Elasticsearch / OpenSearch 的 BM25；
- 方案三：`pg_search` / ParadeDB 这类 PG 扩展原生 BM25。

**取舍依据**：在 372 条这个量级，引入 ES 是纯粹的过度设计。这个判断本身比"我会用 ES"更能说明问题。

## 4. Agent / LangGraph 深挖

### Q4.1 为什么只有 4 个节点？为什么不做多轮对话和工具调用？

**答**：这是**主动的取舍**，不是能力不足。

原计划是 7 节点（含澄清追问、反思重试、工具调用）+ 5 个工具 + 3 周排期。但评估下来：**在有限时间里，一条能讲透、能测量、有降级路径的完整链路，比 7 个半成品节点有价值得多**。所以我收敛到 `parse → search → generate → validate`，把省下的时间投到评估集和消融实验上。

**能指**：`TODO.md` §0.5「三周聚焦计划」、`docs/failed-features.md`。

**这个回答的价值**：面试官最怕的是"什么都想做、什么都没做完"。主动砍范围并说清理由，是资深工程师的行为。

### Q4.2 LangGraph 的状态怎么设计的？为什么要 reducer？

**答**：状态用 `TypedDict` 扁平定义（`backend/agents/state.py`），字段就是 `query / filters / top_k / candidates / recommendations / degradations / node_path / no_solution_reason`。

**扁平的理由**：LangGraph 的状态是每个节点返回增量 dict、由框架合并的。嵌套结构一旦深了，"谁在哪个节点改了哪一层"就说不清了，调试麻烦。

**reducer 的理由**：`degradations` 和 `node_path` 是**累积型**字段——多个节点都会往里追加。如果不用 reducer，后一个节点返回的会**覆盖**前一个节点的值。用 `Annotated[list[str], operator.add]` 后，LangGraph 会把增量**拼接**而不是替换。

**能指**：`backend/agents/state.py`。

**追问：为什么只用 `operator.add`，不用自定义 reducer？** 因为这两个字段只需要追加、不需要去重或转换。`add_messages` 那种带特殊语义的 reducer 现在用不上（没有多轮对话）。

### Q4.3 条件边怎么用的？

**答**：`search` 之后有一条条件边：候选数为 0 时**短路到 `no_solution` 节点直接结束**，不进入 LLM 生成。

**为什么重要**：如果候选为空还把空列表喂给 LLM，LLM 几乎一定会**编造菜谱**。短路不只是一次性能优化，它是防幻觉的第一道闸门。

**能指**：`backend/agents/graph.py` 的 `add_conditional_edges` + 路由函数。

### Q4.4 LLM 解析失败了怎么办？（这是必问的）

**答**：分三层兜底，**任何一层都不会让接口返回 500**：

1. **`parse` 节点**：LLM 返回的 JSON 解析失败 → 重试 1 次 → 仍失败则**降级为"直接用用户原始查询、不加任何约束"**，并往 `degradations` 追加 `parse_intent_failed`。宁可少解析出约束，也不能因为解析失败就不给推荐。
2. **`generate` 节点**：LLM 输出不是合法 JSON → **降级为规则模板生成**（直接用候选菜名 + 固定理由），同时记 `llm_unavailable` + `generate_fallback`（两条递进标签）。用户拿到的是"理由朴素但正确"的结果，而不是 500。
3. **`infra/llm_client.py` 层**：429 / 5xx 做**指数退避重试**（最多 3 次），4xx 不重试（重试也没用）；网络层异常向上抛，由节点捕获降级。

**加分细节**：SiliconFlow 的 chat 返回**习惯性被 ` ```json ` 代码块包裹**，甚至带前后说明文字。所以除了 `strip_code_fence` 剥围栏，还做了"截取第一个 `{`/`[` 到最后一个 `}`/`]`"的兜底，并且**为此专门写了测试**。这是真机跑出来的坑，不是想象出来的。

**能指**：`backend/agents/nodes.py`、`backend/agents/jsonx.py`、`backend/infra/llm_client.py`（`strip_code_fence`）。

### Q4.4b 降级标签的精确契约（`recommendation_shortfall` 到底什么时候出现）

这是被追问答不上来最容易露怯的一处，所以把**真实触发条件**（读代码 + 离线调用真函数验证，非推测）说清楚：

| 标签 | 触发条件（`nodes.py`） |
| --- | --- |
| `parse_intent_failed` | `extract_json_object` 返回 `None`（含重试后仍失败） |
| `generate_fallback` | `node_generate` 拿不到有效 `items`，整段退化为规则模板 |
| `llm_unavailable` | 调用 LLM 抛异常；**会与 `generate_fallback` 同时出现**（两条递进信息，逐条渲染不合并） |
| `citation_invalid` | LLM 给了条目但 `recipe_id` 未精确命中候选，被 `validate_recommendations` 丢弃 |
| `retrieval_degraded` / `retrieval_failed` | 检索器 `degraded` 标记 / 检索抛异常（后者只在 `POST /recipes/search` 有） |
| **`recommendation_shortfall`** | **`len(sanitized) < target`，其中 `target = min(top_k, len(candidates))`** —— **不是硬编码 3** |

**四个必须答准的细节**：

1. **`target` 不是 3**，是 `min(top_k, len(candidates))`（`nodes.py:392`）。线上 `top_k ∈ 1..5`（模型层 `ge=1, le=5`，服务层再 `min(request.top_k, 3+2)`）。所以**候选只有 2 个、请求 3 条时不触发 shortfall**——因为 `target` 就是 2，本来就不该凑到 3。
2. **shortfall 与 citation_invalid 会同时出现**，顺序固定 `['recommendation_shortfall', 'citation_invalid']`。逻辑上必然：非法项被丢弃 → `sanitized` 变短 → 先补 shortfall；同时 `invalid_dropped=True` → 再打 citation_invalid。
3. **shortfall ≠ "LLM 少给"**：如果 LLM 完全输出垃圾（`recommendations` 为空），走的是 `generate_fallback`（`node_generate` 自己用规则填满），validate 层不会再报 shortfall。**典型真机形态是 LLM 返回了 1..target-1 条合法项。**
4. **补齐那条的 `reason` 是固定模板**：`命中你的需求「{query}」的混合检索第 {rank} 名结果`，`missing_ingredients` / `substitutions` 留空、`time_minutes=None`（**不编造缺料和耗时**）。

**我主动承认的一处真实不一致**：同为规则生成的理由，**shortfall 补齐的那条没有后缀**，而 `generate_fallback` 整段兜底的那条带后缀「（未启用 LLM 润色，由规则兜底生成）」（`nodes.py:336`）。用户能看出文案差异。这是既有行为，**没有粉饰成"完全一致"**。

### Q4.4c 已知边界：`parse` 链路遇到 JSON 数组会「取最后一个元素」（未覆盖）

这是我在准备面试时**主动挖出来的自己的坑**，诚实讲比藏着强：

- `node_generate` 的解析器（`_parse_generated_items`）**显式支持裸数组**，有单测（`test_node_generate_accepts_bare_array_payload`）。但**真机没观测到**这个形态（SiliconFlow 实际都返回对象）。
- `node_parse` 用的是 `extract_json_object`，它的包络算法是「第一个 `{` → **最后一个** `}`」（`jsonx.py` 用 `rfind`）。于是模型若返回 `[{"max_time_minutes":30},{"max_time_minutes":5}]`，`json.loads` 拿到的是**只含最后一个元素**的片段 → 结果 `{"max_time_minutes": 5}`。
- **不会崩、不会降级**（因为只判 `payload is not None`），所以**会静默取到末项字段且不打标签**。真机未观测到，**无单测覆盖**。
- **最小修法**：`node_parse` 在 `extract_json_object` 返回 `None` 时再试 `extract_json_array(...)` 取首个元素。

**面试时的说法**：「我知道这里有一个未覆盖的边界——`parse` 遇到数组会静默取末项。generate 链路我写了显式数组支持并加了测试，但 parse 这条我漏了，真机也没触发过。修法很简单（回退到数组解析取首元素），但这是行为变更，当时在冻结期，我没有擅自改。」——**这个回答比"没问题"可信得多。**


### Q4.5 怎么保证 LLM 不编造菜谱？

**答**：**不靠提示词，靠校验**。三道防线：

1. **上下文限制**：`generate` 的 prompt 里只给候选菜谱（含真实 `recipe_id`），并要求输出 JSON；
2. **领域层校验**：`domain.citations.validate_recommendations()` 逐一检查——`recipe_id` 不能空白、不能重复、**必须在候选集合里精确命中**、`name` 必须和候选的 `name` **完全一致**（防止"借壳"，即用对的 ID 配错的菜名）；任何一条不合规就拒绝；
3. **短路**：候选为空时根本不调 LLM（见 Q4.3）。

**为什么放在 `domain/`**：它是**纯逻辑、零 IO**，所以可以直接单测，不需要起数据库、不需要 mock 网络。`domain` 是唯一无 IO 层，校验规则属于业务不变量，天然属于这里。

**能指**：`backend/domain/citations.py`、`backend/tests/unit/test_citations.py`。

### Q4.6 为什么不用 `MemorySaver`？会话状态呢？

**答**：`docs/CONVENTIONS.md` §4.2 明确写了"生产环境用 `PostgresSaver`，禁止 `MemorySaver`"——内存 saver 在多实例部署下状态不共享，而且重启即丢。目前**没有接线会话持久化**（`conversations` / `messages` 表和 `langgraph-checkpoint-postgres` 依赖都已就位，图还没挂 checkpointer），因为没有多轮对话就不需要。

**这是主动推迟，登记在 `failed-features.md`。**

## 5. LLM 工程深挖

### Q5.1 为什么温度设 0.1？

**答**：这个任务的 LLM 只做两件事——**把自然语言翻译成结构化约束**和**从给定候选里挑并解释**。两件都是**抽取/分类**性质，不是创作。温度高只会让 JSON 更容易坏、让理由更飘。所以 0.1。

### Q5.2 token 用量怎么统计的？成本怎么估？

**答**：`RemoteLLM.complete_with_usage()` 返回 `(text, {"input_tokens": n, "output_tokens": n})`，节点把它写进 Langfuse 的 `generation` 观测的 `usage_details`。

**为什么不用 `complete()`**：`complete()` 内部就是调用 `complete_with_usage()` 然后把 usage 丢掉——它是给不需要计量的场景用的。**只要用了 LLM，就应该走 `complete_with_usage` 并记 trace**，否则 Langfuse 的成本/Token 视图是空的。

**能指**：`backend/infra/llm_client.py`、`docs/CONVENTIONS.md` §4.5。

### Q5.3 可观测怎么做的？观察名为什么写成常量？

**答**：`infra/observability.py` 是全项目**唯一**的 tracing 出口，业务代码不允许直接 `import langfuse`。

**观察名做成 `SpanName` 常量类**，因为**观察名是对外契约**——Langfuse 的看板、保存的过滤器、评估器都是按名字匹配的。今天有人在调用点手写一个 `"retrieve"`，明天改成 `"retrieval"`，所有看板静默失效，还查不出来。做成常量后改名就是一次显式的破坏性变更。

**这个设计是踩过坑学的**：`docs/mistakes.md` 里记了 Langfuse 的"先加载 `.env` 再 `import langfuse`"——顺序错了 SDK 会用空凭证初始化，表现为"配了 key 但没有 trace"。

### Q5.4 Langfuse 读取为什么走 Observations API v2？

**答**：2026-09-16 之后创建的 Langfuse 组织访问旧的 `/api/public/traces` 会返回 **410 `LEGACY_API_UNAVAILABLE_FOR_NEW_ORGANIZATION`**。这是真机撞到的，所以项目里统一走 `client.api.observations`（v2）。这条也写进了 `docs/CONVENTIONS.md`。

## 6. 数据工程深挖

### Q6.1 372 篇 Markdown 怎么解析的？难在哪？

**答**：难在**上游是给人看的，不是给程序看的**。具体三个坑：

1. **用量语法不统一**，至少有三种：
   - `鳝丝 400 g`（数值 + 单位）
   - `小龙虾 = 2 斤`（等号 + 中文量词）
   - `椰浆 100ml*份数`（带每份倍数）
2. **中文数词与约数**：`半`、`十`、`两`（=2 斤还是数量 2？）、`约` / `大约` / `差不多` 前缀后缀、`大/小` 尺寸修饰。
3. **有些用量根本不是数字**：`辣椒段的总体积等于兔肉的总体积`、`兔肉斤数 * 2 克`。

**处理原则是"不编造"**：解析不出来的，`amount_min` / `amount_max` 留 `None`，但**原文一定进 `amount_text`**。当前 3,697 条食材里有 **25 条**用量解析不出来，全部登记在 `import_report.json` 里等人工确认。（**这是清理解析噪声前 86 条 → 现在 25 条**：原来的 86 条里有 61 条根本不是食材行，而是「盐的用量为」「一碗容量是」这类说明句。）

**能指**：`backend/scripts/import_howtocook.py`、`data/recipes/import_report.json`、`backend/tests/unit/test_import_howtocook.py`（235 行测试）。

### Q6.2 食材归一化怎么做？命中率多少？剩下 26.5% 呢？

**答**：词表在 `data/ingredients/aliases.yaml`（115 个标准食材 / 294 个别名 / 共 409 种写法），匹配策略在 `domain/ingredients.py`，**保守、可预测、绝不猜**：

1. 清洗（NFKC 全角转半角 → 去括号备注 → 去空白 → 去尾部标点/「的儿」/「量」）
2. 精确匹配标准名或别名
3. 去**处理形态后缀**再匹配（`蒜末` → `蒜`、`土豆片` → `土豆`）
4. **前缀匹配但有两道保险**：别名至少 2 个字（否则 `蛋` 会把 `蛋糕` 吸过来、`水` 会吸 `水果`）；剩余部分首字如果属于 `油/酱/汁/粉/醋/酒/糖/盐/米/面/豆/奶/肉/鱼/虾/蛋/菜/果` 就**拒绝**匹配（`花生油` 绝不能变成 `花生`）
5. 都不中 → 返回 `None`，进报告等人工补

**当前真实数字**：**3,697** 条里 **2,784 条命中（75.3%）**，未收录 **748 种**写法。

**关键的高分回答（必须说）**：**未命中的主体不是"词表不够大"，而是解析器把说明文字当成了食材。** 我最初的 `unmapped_top` 里混着 `工具`、`原料:`、`盐的用量为`、`一般一个人可以食用`、`肉量`、`厨房纸`、`手动压汁器`、`葱、姜、蒜` 这种东西。

所以我做的**不是往词表里塞垃圾来提高命中率**（那会让指标好看但数据更脏），而是**在解析层加过滤**：章节小标题丢弃、说明句丢弃、工具归 `recipe.tools`、并列写法拆分。**词表一个词都没加**，归一化率从 73.5% 升到 **75.3%**，未收录种数从 856 降到 **748**，`unmapped_top` 里的噪声**全部消失**。

**追问：为什么归一化率会「上升」？** 因为分母里的垃圾被删掉了（食材条目 3,902 → 3,697），而真食材的命中数基本不变（2,867 → 2,784）——**下降的那部分是原本被误当食材的说明行**。这不是刷指标，是修数据。

**追问：怎么保证过滤规则没误杀真食材？** 有一条真实的反例守住了：`盐量 = 兔肉斤数 * 2 克` 里的 `盐量` / `肉量` / `油量` **必须保留**——「量」结尾不等于说明句，只有「**用量**」才是。这条专门写了参数化测试（`test_ingredient_names_ending_with_liang_survive`）。**如果我图省事写 `if name.endswith("量"): return ""`，就会静默吃掉一批真食材。**

**能指**：`domain/ingredients.py`、`import_report.json` 的 `unmapped_top`。

**已知边界（面试主动说，比被问出来强）**：当前词表把原材料和加工制品当**平级独立条目**——`番茄`（蔬果）和 `番茄酱`（调料）、`土豆`（蔬果）和 `土豆淀粉`（调料/淀粉）互不归属。这导致用户说"不要番茄"时，含番茄酱的菜漏过滤（详见 Q3.2 的"漏网"追问）。这不是 bug，是词表设计粒度的取舍：加父子层级（番茄酱 → 父=番茄）能解决忌口语义，但会让购物清单合并逻辑变复杂。当前选择是"先把精确匹配做对，层级关系留到下一版"。

### Q6.3 幂等怎么保证的？

**答**：分段策略，写在 `scripts/seed_recipes.py` 的模块 docstring 里：

| 表 | 冲突键 | 策略 |
| --- | --- | --- |
| `ingredients` | `name` | `ON CONFLICT DO UPDATE` |
| `ingredient_aliases` | `alias` | `ON CONFLICT DO UPDATE`（重指向标准食材） |
| `recipes` | `id`（由 `source_path` 派生的**确定性 UUID**） | `ON CONFLICT DO UPDATE` |
| `recipe_ingredients` / `recipe_steps` | **无天然唯一键** | 先按 `recipe_id` 删干净再插入 |

**关键点是 `recipes.id`**：它不是随机 UUID，是**从 `source_path` 派生**的。所以同一篇 Markdown 重跑一次，得到的还是同一个 ID，其他表的外键才稳定。这是"重跑不产生脏数据"的基础。

**追问：删干净再插不是有并发风险吗？** 是。当前是单机脚本、单事务，没有并发写。如果变成在线服务需要改成 upsert + 软删，或者用 staging 表 + 原子切换。

## 7. 评估与实验深挖（**最能拉开差距的部分**）

### Q7.1 评估集怎么建的？有什么问题？

**答**：`data/eval/queries.yaml`，**40 条**中文查询，分 5 类各 8 条：①直接菜名 ②食材组合 ③场景/耗时 ④口味/菜系 ⑤工具/做法。每条标注 1~3 个相关菜谱，**标注的菜名必须用脚本校验在库里真实存在**。

**我必须主动承认的局限**：

- **是我一个人标的**，所以是"一人标注"，没有标注者间一致性（Kappa）数据；
- **40 条是小样本**，只能做相对比较（哪组更好），不能当绝对质量结论；
- **相关度是二值**（相关/不相关），nDCG 里把相关度都当 1，所以 nDCG 和 Recall 高度相关，信息量有重叠。

**改进方向**：扩到 200+ 条、做双人标注 + Kappa、引入分级相关度。

> **这个回答的价值**：能主动说清自己评估的局限，比报一个漂亮数字可信得多。

### Q7.2 消融怎么做的？结论是什么？

**答**：三组，用同一个候选池大小保证可比，只换检索策略：

| 模式 | 含义 |
| --- | --- |
| `vector` | 纯向量（BGE-M3 余弦 Top-N），基线 |
| `hybrid` | 向量 Top50 + BM25 Top50 → RRF |
| `hybrid_rerank` | 混合 + bge-reranker-v2-m3 重排 |

指标：Recall@5、Recall@10、MRR@10、nDCG@5，外加单查询延迟中位数与 P95。

**结论以 `data/eval/reports/*.json` 的实测输出为准**，一跑就知道：

```bash
cd backend && .venv\Scripts\python.exe -m scripts.eval --mode all
```

**能指**：`backend/scripts/eval.py`、`README.md` 的「评估结果」表。

### Q7.3 为什么延迟只报中位数和 P95，不报平均值？

**答**：检索延迟是**右偏分布**（大部分请求快，少数因为网络往返/冷启动很慢），平均值会被长尾拉高，既不代表典型体验也不代表最差体验。**中位数代表典型，P95 代表"大多数用户会遇到的最差情况"**，这才是对 SLA 有意义的。

**而且我们踩过冷启动的坑**：`docs/mistakes.md` 里记了首查询 1668ms、稳态 342~438ms——原因是首次远程重排包含 TCP/TLS 建连和模型侧冷启动。所以报延迟必须说明"是冷启动还是稳态"，否则数字没有意义。

### Q7.4 混合检索一定比纯向量好吗？

**诚实答：我的实测结论是「在我的语料上更差」，而且我把根因定位到了一个结构性缺陷。**

40 条评估集上的实测：`hybrid` 全面差于纯向量（R@5 61.25% vs 63.75%、R@10 68.75% vs 72.08%、MRR 70.86% vs 74.00%）。

**我先猜错了。** 我最初的假设是「BM25 把字面相似但不相关的菜顶进了头部」，但逐条比对三元组 `{向量名次, BM25 名次, RRF 名次}` 后，**这个假设被数据否定了**。真实机制是一个纯数学的结构性事实：

```
等权 RRF，k=60，候选池 Top50
  单通道项上界 = 1/(60+1)  = 0.016393   ← 只被一路召回，哪怕排第 1
  双通道项下界 = 2/(60+50) = 0.018182   ← 两路都召回，哪怕都排第 50
  → 0.018182 > 0.016393 恒成立
```

**只要一道菜两路都进 Top50，它必然排在所有单通道候选之前。** 7 条回归查询的 21 个金标准通道来源：**双通道 7 / 仅向量 13 / 仅 BM25 0 / 两路均未召回 1**。拉开差距的正是「仅向量」那 13 个——向量明明把它们排得很靠前，却因为 BM25 没召回它们，被整片「双通道共识集合」压到后面：

| 查询 | 金标准 | 向量名次 | BM25 | RRF 名次 |
| --- | --- | --- | --- | --- |
| 家里只剩鸡蛋和番茄 | 西红柿炒鸡蛋 | **1** | 未召回 | **22** |
| 想用烤箱做点甜点 | 戚风蛋糕 | **1** | 未召回 | **21** |
| 想吃川菜，要麻辣一点 | 麻婆豆腐 | **3** | 未召回 | **17** |

7 条回归查询的 Top10 里 **88.6%（62/70）是双通道共识项**；全量 40 条的 **Top5 里双通道占 92.5%**，而 BM25-only 全程只贡献了 11/400 个位置。

**所以准确的表述是**：混合检索的伤害不是「BM25 有噪声」，而是 **RRF 只用名次、完全不看通道可靠性**——BM25 任何一次命中都会把该菜升格为「共识项」并获得永久优先权。**在 BM25 召回率本就低的语料上，这等价于系统性惩罚向量通道。**

**追问：那你为什么还留着混合检索？** 两个原因，都很诚实：① 关键词通道对**精确菜名**和**生僻词**有兜底价值（`direct` 类三组都是 100%，但这类查询向量本来就够好）；② 改 `w_bm25` 属于 `rag/fusion.py` 的接口变更，我做了权重敏感性实验（`w_bm25 ∈ {0, 0.25, 0.5, 1.0}`）但没有擅自改默认值——**有证据的次优默认值，也好过没证据的"优化"**。

**追问：那你建议怎么办？** 两个方案，都有数据支撑：
- **主指标优先**：`w_bm25 = 0.0`（纯向量）。R@5 / MRR / nDCG@5 三项都是它最好，**没有任何权重能翻盘**。
- **必须保留关键词通道**：`w_bm25 = 0.25`。它是**唯一**在 R@10 上超过纯向量的配置（74.17% vs 72.08%，+2.09pp），代价是 R@5 −1.67pp、MRR −2.73pp。
- **明确不要保留 `1.0` 等权**——它是所有配置里最差的之一。

**追问：那把各通道深度截断（只取 Top10）能救吗？** **不能，我有实测**：它把双通道集合从 349 项砍到 126 项、头部共识占比从 87.3% 压到 **31.5%**，**但 R@5 仍然是 61.25%，一点没变**；代价是把 **26 个**金标准踢出候选池（从 12 涨到 26）。**结论：截断尾部换来的精度收益，被截断掉的召回损失完全抵消——想修 RRF 的头部，靠调召回深度没用，必须改融合公式。**

**这个回答为什么值钱**：它展示了「提出假设 → 用数据否定假设 → 找到真正的机制 → 做参数敏感性实验 → 给出有依据的建议但不动冻结代码」的完整过程。比说一句「混合检索效果更好」强得多。

### Q7.5 你的评估结果可复现吗？有没有你不知道的抖动？

**诚实答：分开说——`vector` 和 `hybrid` 完全可复现，`hybrid_rerank` 不可复现到小数点。**

- **`vector` / `hybrid` 是确定值**：同输入必得同结果（中间没有非确定性组件）。
- **`hybrid_rerank` 会抖**：远端 bge-reranker 的服务端打分对同一输入**并非逐位确定**。同一语料、同一脚本连跑 3 次实测极差：R@5 **0.00pp**、R@10 **0.83pp**、MRR **0.0042**、nDCG@5 **0.0025**（R@10 在 77.50% / 78.33% / 78.33% 之间跳）。**40 条里有 12 条的 Top10 顺序被改写**（集合基本不变），其中 2 条的指标真的变了。
- **所以 README 里那一行写成了区间**（R@5 64.2% / R@10 77.5–78.3%），并在表下注明「不要把小数位当精度」。**表里有区间的格子 = 连跑 3 次的极差**，这个约定本身也要讲清楚，否则读者不知道哪些数字可比。
- 原始逐查询比对留底在 [`docs/evidence/rerank_variance.txt`](./evidence/rerank_variance.txt)，复现脚本 `backend/scripts/rerank_variance.py`。

**更值得说的一点：延迟的 P95 在 n=40 时是不可信的。** `vector` 那一行 p95 = 859 ms，但它的中位数只有 152 ms——**P95 完全由单个离群点（某条 956 ms）决定**。所以我在 README 里明确写了「延迟只用于三组之间的相对比较，不要当 SLA」。**知道自己指标在什么情况下不成立，比报一个漂亮的 P95 更重要。**

**为什么值得主动说**：面试官如果自己复现发现数字不一样，会怀疑你造假。**主动交代抖动范围，比给一个"精确"的三位小数可信得多。** 而且这也说明我知道「什么时候该怀疑自己的测量工具」。

**追问：怎么判断某次跑的数字不能用？** 检查报告的 `provider_stats.degraded_calls`。若不为 0，说明该次重排走了本地兜底（或降级回 RRF），**数字不可比**。本会话早前确实撞到过一次 `/v1/rerank` 503 并降级——那次的数据我直接丢弃重跑，没有拿去用。

### Q7.6 Recall@5 只有 63.75%，你原本的目标是多少？

**诚实答：README 早期版本写过「Recall@5 ≥ 85%」，那是没有测量支撑的目标值——现在已删掉，改成实测值加差距归因。**

差距 21pp 的来源，按贡献排序（**都不是排序算法**）：

1. **金标准集不完整（最大项）**：每条查询只标 1–3 个相关菜，而库里存在大量同样满足约束的合法答案。启发式估算显示 Top10 里「未标注但按查询约束看确实合法」的占比很高（若标注完整，precision@10 约为 54.6% / 56.2% / 65.8%），**所以 Recall 被系统性低估**。
2. **scene / taste 类没有结构化元数据**：评估时结构化 `time_minutes` **372 行全为 NULL**（解析遗漏，不能归因于上游全无时长）、`tools` 非空仅 82 行；简介仍可能含时长原文，但结构化时间过滤不可用（三组都只有 16.7%–50%）。
3. **剩下的才是排序问题。**

**关键是我没有为了接近 85% 去调参或改标注。** 面试时这句话必须说出来——**指标不好看可以解释，造假解释不了。**

### Q7.7 端到端延迟你报的是多少？为什么给区间？（**很好用的一题**）

**答：`/recommend` 9.2–12.0 s（极差 2.8 s），纯检索 0.37–0.44 s（极差 70 ms）。同一份代码、同一份语料连跑三轮。**

这题的价值在于它能把「测量素养」讲透，而我确实被自己的第一版数据坑过两次：

**坑一：探针写死了响应字段名，把 5 条候选报成 0 条。** 我第一次跑 `/recipes/search`，探针读 `data["results"]`，而契约字段是 **`candidates`** → 打到 `None` → 打印 `results=0`、`top3=[]`。**HTTP 200、`degraded=false`，看起来完全像"检索真的没召回"**，差点被我当成一条新发现写进 README。后来做了三件事：① 探针改成"按字段是否存在自动适配"（`candidates` / `results` 都认）；② **加了 `describe_fields()`，把响应的顶层字段名和条目数打出来**——有这一行，「`candidates=0`」和「响应里根本没有 `candidates` 键」在人眼里就是两件事，这类事故从根上被堵住；③ 误报那次的原始输出**入库保留**为 `docs/evidence/e2e_run1_OLD_PROBE_field_bug.txt`——留着它比删掉有价值。

**坑二：LLM 的不确定性会污染延迟，也会污染 `degraded`。** 三轮里两轮 `degraded=false`、一轮 `degraded=true` + `recommendation_shortfall`（同一句话，模型有时只返回 2 条推荐，触发规则补齐）。而同一批跑里**无解路径稳定 2.1–2.3 s（极差 0.2 s）、纯检索稳定 0.37–0.44 s（极差 70 ms）**。所以：

- **波动全部来自 LLM 生成阶段，检索侧几乎确定**；报延迟时不能把两者混成一个数。
- README 的端到端表**改成给区间 + 极差**（`9.2 – 12.0 s（极差 2.8 s）`），并注明区间来源就是生成阶段。**一个三位小数的"精确值"是假精度**——一次测量无法代表方差。
- 区间不是我手挑的：`backend/scripts/e2e_latency_summary.py` 读全部 `e2e_run*.txt` 自动聚合，并**硬性排除**已知有 bug 的轮次（`OLD_PROBE`）。**"排除依据写在脚本里"比"我在文档里解释一句"更可靠。**
- 结论：**任何含 LLM 往返的指标，默认多次运行给区间**；这条已经写进 `docs/mistakes.md` 作为仓库规矩。

**能指**：`backend/scripts/e2e_probe.py` + `e2e_latency_summary.py`（可复现，已入库并带单测）、`docs/evidence/e2e_run{2,3,4}.txt` + `e2e_latency_summary.txt` + `e2e_run1_OLD_PROBE_field_bug.txt`（原始输出入库）。

### Q7.8 你怎么保证 README 里的数字没有跟证据脱节？（**这题能问出"工程化"和"喊口号"的差别**）

**答：因为我一开始只是"在文档里写了要求"，后来把要求变成了"跑一条命令就知道"。**

`docs/CONVENTIONS.md` §4.6 从 v1.11 起就写着「正文数字必须能追到 `docs/evidence/` 的原始输出」。但这句话当时**只是文字**——我手工比对过一次，比对完就结束了，**没有任何命令或 CI 会在两者对不上时报错**。两种失败方式都拦不住：

1. 改了 README 的数字，忘了同步证据；
2. 手写一个"看起来差不多"的区间——比如实测 `77.50–78.33%`，我写成 `77.5–79.0%`。

所以补了 `backend/scripts/check_docs_consistency.py`，三类对账，任何一件不过就 exit 1，**已作为独立步骤进 CI**：

| 检查 | 抓什么 | 为什么不能用更弱的形式 |
| --- | --- | --- |
| 指标格对账 | README 评估表 12 个格子 vs `eval_reports_summary.json` | 摘要里带 `sha256_16`，能绑定到具体那一份报告文件 |
| **区间来源对账** | `hybrid_rerank` 的区间必须**恰好等于** `rerank_variance.txt` 的跨轮极差 | ⚠️ **写测试时我发现自己差点漏掉**：如果只检查"区间覆盖报告值"，把 `70–80%` 写进去也能覆盖 `77.50%`，检查会**放行**。"覆盖得住"不等于"有依据"——区间必须等于实测极差 |
| 来源标注对账 | README 引用的每个 `docs/evidence/...` 路径必须真实存在 | 防止悬空引用（指向已删除/改名的证据） |

**我专门验证了门禁本身不是摆设**：把 README 的 R@5 改成 `99.99%` → exit 1，报 `纯向量 / R@5：README 写 99.99%，证据报告是 63.75%`；把某个来源改成不存在的文件 → exit 1。这两条也固化成了单测——`test_check_docs_consistency.py` 共 28 项，**其中一半是"注入错误必须报错"**。

> **一个永远返回 0 的检查器比没有检查器更糟**，因为它提供虚假的安全感。所以门禁自己必须有"注入错误会失败"的测试。

**能指**：`backend/scripts/check_docs_consistency.py`、`backend/tests/unit/test_check_docs_consistency.py`（28 passed）、CI 的 `Docs consistency gate` 步骤、`docs/mistakes.md` 的 W3.8 条目。

## 8. 工程素养深挖

### Q8.1 覆盖率多少？怎么算的？

**答**：**96%**（`TOTAL 1669 statements, 66 missed`，547 passed / 4 skipped），门禁 `--cov-fail-under=70`。

**口径很关键**：我们**刻意不把 `tests/` 和 `scripts/` 算进覆盖率**。一开始用 `--cov=.`，测试文件自身也被统计进去，数字被稀释、也不说明任何问题。改成只统计生产代码（`domain/rag/infra/core/api/agents/services/main.py`）后，这个数字才真的代表"业务逻辑被测了多少"。

**从 93% → 96% 是补出来的，可以讲过程**：我先把 `--cov-report=term-missing` 的**低覆盖模块挑出来**，发现三个都不是"环境不可测"，而是"没人写测试"：

| 模块 | 前 | 后 | 怎么补的 |
| --- | --- | --- | --- |
| `infra/db.py` | 64% | **100%** | 关键认知：`create_async_engine` 是**惰性**的，只建对象不建连接 → **单测根本不需要真库**。用假 session/factory 覆盖 commit / rollback / 建连失败三条分支 |
| `infra/observability.py` | 75% | **94%** | 之前只跑了"没配 key 降级"那一支；注入**假 langfuse 模块**后覆盖启用路径。剩 6 行是 SDK 真发请求后的分支，不追求 100% |
| `api/deps.py` | 80% | **100%** | 装配链（engine → corpus → retriever → service）与「关闭失败只记日志」的 except 分支 |

**补测试时踩到一个真坑（值得主动说）**：`observability.configure()` 的启用路径会往 `os.environ` 写 `LANGFUSE_PUBLIC_KEY`，而 pydantic-settings 的 `_env_file=None` **只关 `.env` 文件、关不掉真实环境变量**。结果单独跑全绿、**大全量跑时 6 个用例红**——典型的**用例间顺序依赖**。修法是 autouse fixture 里保存/还原 `LANGFUSE_*`，并且构造 `Settings` 时显式传 `None`（初始化参数优先级最高）。

**这个坑为什么值钱**：它说明"测试通过"要看**在什么顺序、什么范围下通过**。单跑绿、全量红，比全红更危险——如果我只跑单文件就提交，CI 才会抓到。

**能指**：`.github/workflows/ci.yml` 的 pytest 步骤、`tests/unit/test_infra_db.py`、`tests/unit/test_infra_observability.py`、`tests/unit/test_api_deps.py`。

### Q8.2 测试怎么分层的？集成测试怎么保证不污染数据？

**答**：

- **单元测试**（`tests/unit/`）：不碰网络、不碰数据库。纯函数（RRF、指标、分词、归一化）+ 用 `httpx.MockTransport` 假掉外部 HTTP（LLM / embedding / rerank）+ 把 SQL 编译成字符串断言谓词（不需要真库）。
- **集成测试**（`tests/integration/`）：需要真库，用 `pytest.mark.skipif` 在库不可用时**跳过而不是失败**（别人 clone 下来没有 Docker 也能跑通全部单测）。
- **数据隔离**：集成测试在事务里跑，`await transaction.rollback()` 收尾，**不留数据**。

**集成测试的一个巧思**：测试混合检索时，直接从库里取某道菜的**真实 embedding 当查询向量**，这样向量通道必然把它排第一，就能端到端验证整条管线（而不是 mock 掉向量检索）。

**能指**：`backend/tests/integration/test_retriever.py`。

### Q8.3 分层是怎么强制的？有没有被破坏过？

**答**：规则是 `api → services → domain / agents / rag → infra` 单向。目前靠**代码审查 + Protocol 契约**保证，没有用 import-linter 之类的工具自动强制。

**已知的边界情况**：`infra` 可以 import `domain`（Protocol 方向是对的），但 `domain` 不能 import 任何层。`rag/` 只做编排（切分、检索、融合、索引），**不直接持有模型客户端**——模型客户端在 `infra/`，通过构造参数注入。

**诚实补充**：如果有更多时间，应该引入 `import-linter` 把这条规则做成 CI 门禁，而不是靠人盯。

### Q8.4 错误处理怎么设计的？

**答**：统一的错误信封 `{code, message, status, request_id}`（`core/exceptions.py` 的 `ErrorResponse`），三层兜底：

1. `AppError` → 显式 4xx，业务可预期；
2. `RequestValidationError` → 统一 422，不暴露 pydantic 的内部错误细节；
3. 兜底 `Exception` → 500，**只返回 `internal_error`，绝不返回 traceback**，但服务端日志里记完整堆栈。

**`request_id`**：接受客户端传入（便于全链路对齐），但必须校验——长度 ≤ 128、无空白字符、可打印，非法就换成新生成的 UUID。这样既支持分布式追踪，又不会被注入脏 header。

**能指**：`backend/main.py`、`backend/tests/unit/test_main.py`（有专门的非法 request-id 参数化测试 + 断言响应里没有 traceback）。
